# Hardening Plan — Security Review Follow-ups

**Status:** Active tracking doc
**Origin:** Two independent reviews of the repo (2026-08-05) — a red-team security pass and an architecture/positioning pass — cross-checked against actual code, not taken at face value. Findings below are only the ones verified against `apps/api/src`.
**Relationship to other docs:** Extends the roadmap in `CLAUDE.md` and the milestone plan in `docs/SIGNAL_ALPHA_DESIGN.md` §10. That design doc predates some of the current implementation — risk engine, order preview/approval, and audit log (its Milestones C, D, F) already exist in code. This doc tracks what's left, not what to build from scratch.

Check items off as they land. Each item notes which review raised it and whether it's a hard gate on Phase 4 (live IBKR execution).

## Verified current state (as of this review)

Already implemented and confirmed by reading the code (not just claimed):
- Scanner → composite score → watchlist (`scanner/runner.py`, `ranking/scorer.py`)
- Thesis agent with "never recommend buy/sell" system prompt, JSON schema output, `input_hash` caching, `AgentRun` logging on non-cached calls (`ai/thesis_agent.py`)
- Deterministic risk engine, 13 rules incl. kill switch, no margin/options/shorting, position/sector/loss limits, earnings proximity, cooldown (`risk/rules.py`)
- Order preview → risk evaluation → human approval → paper trade (`orders/service.py`)
- Audit log written in the same DB transaction as the state change (`audit/service.py`)
- Finnhub news categorization with keyword fallback (`data/finnhub.py`)
- `IBKRClient` already has session/auth, contract search, market data, **and** `get_accounts`, `get_positions`, `place_order`, `get_orders` (`data/ibkr.py`) — these are written but **not called from anywhere else in the codebase**. (Correction: an earlier pass of this doc also claimed `cancel_order` existed; it doesn't — checked while building the adapter isolation below.) This is further along than it looks; the gap is wiring + isolation, not missing implementation.

What's missing entirely: any authentication/authorization layer, an agent tool/MCP-style gateway, realistic paper fills, and a real (non-paper) portfolio provider.

## Phase 3 (current) — hardening before Phase 3 is "done"

These are gaps in what's already built, not new scope.

- [x] **P0 — Add authentication + authorization to the API.** *(Red-team #1, #7)* — Done: shared-secret `X-API-Key` auth (`broker/auth.py:require_actor`), applied via `dependencies=` to every router except `/health` (`main.py`). `X-Actor` header now flows into `approved_by` on order/paper-trade approve/reject and into `audit_log(actor=...)`, replacing the hardcoded `"human"`. Frontend sends both headers from `apps/web/src/lib/api.ts` (`NEXT_PUBLIC_API_KEY` / `NEXT_PUBLIC_ACTOR`, gitignored `.env.local`). Verified: `/health` returns 200 unauthenticated, `/universe` returns 401 with missing/wrong key.
  - Remaining (not done): this is a single shared secret, not per-user auth — no real scopes (viewer/researcher/approver/admin) and no step-up confirmation. Fine for single-operator use per `SIGNAL_ALPHA_DESIGN.md` §11, but revisit before multi-user or public exposure.
- [x] **Harden JSON parsing in the thesis agent.** *(Red-team #7)* — Done: added `ThesisResponse` pydantic model (`ai/thesis_agent.py`) validated against `json.loads(raw_text)`; on `JSONDecodeError`/`ValidationError`, one retry with an explicit "return valid JSON" note appended to the prompt. If the retry also fails, raises `ThesisParseError` — no `StockThesis` row is ever created, and both raw attempts are stored on `AgentRun.output_json` (`raw_attempts`) before the outer `generate()` handler commits `run.error`. Token usage (`AgentRun.prompt_tokens`/`completion_tokens`) now accumulates across both attempts. Verified with a mocked Anthropic client: retry-then-succeed produces a valid thesis; retry-then-fail raises cleanly with both attempts preserved and no partial thesis row.
- [x] **Treat news content as untrusted input in the thesis prompt.** *(Red-team Scenario B)* — Done: `_SYSTEM_PROMPT` (`ai/thesis_agent.py`) now explicitly tells Claude the `<news_articles>` block is untrusted third-party data, not instructions, and to never follow directives found inside it. `_build_user_prompt` wraps news in `<news_articles>...</news_articles>` delimiters and strips any literal occurrence of those tag strings from the article text first, so an adversarial headline can't forge a fake closing tag and escape the block. Verified: a synthetic headline containing `</news_articles>` and injected "SYSTEM:" text is neutralized — the tag markers are stripped from the content and the real delimiters stay balanced (1 open / 1 close).
- [x] **Preview staleness / re-pricing at approval time.** *(Red-team Scenario C; also flagged as an open question in SIGNAL_ALPHA_DESIGN.md §15)* — Done: `settings.order_preview_ttl_minutes` (default 5, `.env.example`). `approve_preview` (`orders/service.py`) now rejects with `PreviewExpired` (→ 409) if `created_at` is older than the TTL — preview status is left untouched so the client must request a fresh preview rather than the system guessing a new price. Independently, the risk engine is now always re-run at approval time against current portfolio state/cooldowns/kill-switch (not just at preview time); if the re-evaluation verdict is `blocked`, the preview is flipped to `status="blocked"`, audit-logged (`approve_order_blocked_on_reeval`), and `PreviewBlockedAtApproval` is raised (→ 409) instead of silently approving. Verified against the real dev DB: (1) a fresh preview still approves normally, (2) a backdated (>TTL) preview is rejected and left `pending`, (3) engaging the kill switch between preview and approval correctly blocks approval on re-eval and persists `status="blocked"`.
  - Note: this bounds *portfolio-state* staleness, not *price* staleness directly — `limit_price` is not silently re-fetched (that would change what the human is approving); the TTL is what forces a fresh preview at a current price once it lapses.
- [x] **Upgrade paper fill realism.** *(Red-team #3, Scenario D)* — Done: `execution/paper_adapter.py`'s `simulate_fill()` now takes action/limit_price/requested_shares/avg_daily_volume and returns a `FillResult` (status, filled_shares, fill_price, theoretical_price) instead of echoing the limit price. Adverse slippage (`PAPER_FILL_SLIPPAGE_BPS`, default 5bps) is applied against the trader on every fill — BUYs fill above the limit, SELLs below. When requested size is large relative to 20-day ADV, entries (BUY) partial-fill on a linear ramp between `PAPER_FILL_PARTIAL_ADV_PCT` (10%) and `PAPER_FILL_REJECT_ADV_PCT` (25%, full rejection) — floored at `PAPER_FILL_MIN_PARTIAL_RATIO` (30%). `orders/service.py::approve_preview` now: rejects the fill outright (`FillRejected` → 409, `preview.status="rejected"`, audited as `approve_order_fill_rejected`) when size is too large for liquidity; records `PaperTrade.requested_shares` / `theoretical_entry_price` / `theoretical_exit_price` / `fill_status` alongside the existing `shares`/`entry_price`/`exit_price` so theoretical (naive limit-price) vs. executable performance can be compared directly per trade. New columns added via migration `a3c7e1f2b4d6_add_fill_realism_columns`. Verified against the real dev DB across four scenarios: small order fills in full with slippage; oversized order (15% of ADV) partial-fills; very large order (33% of ADV) is rejected with no trade/paper_trade row created and the preview left `rejected`; a SELL exit prices with adverse slippage against the trader.
  - Scoped down from the original ask: **partial fills are entry-only (BUY)**. Exits (SELL) either fill in full (with slippage) or are rejected outright — `PaperTrade` has one entry price/date and one exit price/date, so a position closed across two different exit fills would need the trade row split, which is a bigger schema change than this pass covers. **Next-bar fill is not implemented** — the simulator only ever prices at approval time and has no notion of a subsequent bar relative to that instant; would need order timestamps decoupled from approval timestamps to mean anything. Both are noted in `paper_adapter.py`'s docstring as deliberate scope cuts, not oversights.
- [x] **Fix scoring signal labeling / confirm no product-facing overclaim.** *(Second review's scoring claim was slightly overstated; low-priority accuracy check, not a functional bug.)* — Checked, no fix needed: `ranking/scorer.py` computes exactly four weighted sub-scores (`volume` 25%, `momentum` 35%, `rs` 30%, `gap` 10%); RSI-14 and SMA-50/200 are already correctly folded into `_momentum_score()` as inputs, not scored/weighted independently. `docs/USER_GUIDE.md` §"How scoring works" already states this precisely — a table listing the four sub-scores with the Momentum row spelling out "RSI-14 position, 1-day/5-day price change, above SMA-50/200" — and separately documents the boolean `signals_fired` flags (`rsi_momentum`, `above_both_smas`, etc.) as a distinct concept from the weighted sub-scores, matching `scorer.py`'s `signals` dict exactly. `README.md` and `SIGNAL_ALPHA_DESIGN.md` both describe scoring only at the "volume/momentum/RS/gap" level, no deeper claims. The only frontend surface showing RSI (`apps/web/src/app/scanner/page.tsx`) renders it as its own raw-value column next to Score, not as a labeled sub-signal — doesn't imply independent weighting. Conclusion: the second review's claim didn't hold up against the current docs/code; no changes made.

- [x] **Kill switch / autonomy mode API.** *(Surfaced while scoping the Phase 5 agent gateway item below — not originally in this doc.)* — Done: `AgentControl.is_killed`/`killed_reason`/`autonomy_mode` already existed and were already read by `risk/rules.py::check_autonomy_mode` and the kill-switch rule, but nothing let anyone set them except a direct DB edit. New `agent_control/service.py` (`get_or_create_control`, `kill`, `unkill`, `set_autonomy_mode`) and `routers/agent_control.py`: `GET /api/v1/agent-control`, `POST /api/v1/agent-control/kill` (`{reason}`), `POST /api/v1/agent-control/unkill`, `POST /api/v1/agent-control/autonomy-mode` (`{mode}`, validated against `research_only`/`paper_only`/`preview_required`, 422 on anything else). Every change is audit-logged (`agent_kill`/`agent_unkill`/`agent_autonomy_mode_change`) and records `updated_by` from `X-Actor` (new column, migration `a9c2e4f6b8d0`). Verified against the real dev DB and running server: `GET` auto-creates the singleton `global` row on first call; kill → `is_killed=true` persists and is audit-logged; unkill restores it; invalid autonomy mode returns 422 without touching the row; and, most importantly, an end-to-end `create_preview` call while killed actually gets `status="blocked"` with `check_autonomy_mode`'s kill-switch reason in the risk evaluation — confirming this isn't just CRUD on the column, it actually gates trade proposals through the existing risk engine wiring.
  - Scope note: this is a global on/off switch and one shared autonomy mode, matching `AgentControl.scope` as it exists today (always `"global"`) — no per-agent or per-ticker granularity, consistent with everything else in this codebase being single-operator scope for now.

## Phase 3 → Phase 4 gate — must be true before any live-IBKR wiring starts

These map to the architecture review's "Immediate PRs" and the red-team's P0 blockers #2 and #4. None of this is urgent for Phase 3, but none of it should be skipped when Phase 4 starts.

- [x] **Isolate broker execution behind an adapter interface + feature flag**, per `SIGNAL_ALPHA_DESIGN.md` §9/§16. — Done: `execution/base.py` defines `BrokerAdapter` (ABC, `submit_order(...)`) and the shared `FillResult` dataclass (moved out of `paper_adapter.py` to avoid a circular import between the two adapters). `execution/paper_adapter.py::PaperAdapter` implements it by delegating to the existing `simulate_fill()`. `execution/ibkr_adapter.py::IBKRAdapter` also implements it, but is a **structural placeholder only** — `submit_order` raises `LiveTradingDisabled` when `settings.enable_live_trading` is false (the default), and raises `NotImplementedError` even if the flag is set, since per `CLAUDE.md` no live-trading code (i.e. an actual `IBKRClient.place_order` call) is allowed to exist before Phase 4. `orders/service.py::get_broker_adapter()` is the single seam that could ever route to live execution, and it unconditionally returns `PaperAdapter()` today — Phase 4 wiring changes this one function, not the call sites. `ENABLE_LIVE_TRADING` env var added (`.env.example`, default `false`), currently inert. `OrderPreview.execution_mode` column added (`paper`/`live_preview`/`live`, default `paper`, migration `e5f9a2c1d3b7`) so previews are labeled for when Phase 4 needs to branch on it. Corrected one earlier review claim while implementing this: `IBKRClient` (`data/ibkr.py`) has `place_order`/`get_orders` but **no `cancel_order`** — the earlier "already has ... cancel_order" note in this doc's "Verified current state" section was inaccurate; not adding it now since nothing calls it yet.
  - Verified against the real dev DB: `PaperAdapter`/`IBKRAdapter` both satisfy `isinstance(_, BrokerAdapter)`; `IBKRAdapter.submit_order` raises correctly in both flag states; `get_broker_adapter()` returns `PaperAdapter` regardless of the flag; a full `create_preview` → `approve_preview` run with `IBKRAdapter.submit_order` patched to raise on any call completes successfully and the patch is never triggered — proving paper approval cannot reach the IBKR live-order path.
  - **IBKR connection model — decided, not open:** `ibkr_adapter.py` stays on the local **Client Portal Gateway** (manual 2FA, matches `CLAUDE.md`), not IBKR's OAuth Web API. OAuth Web API would remove the local-gateway dependency, but only matters if Signal Alpha becomes a multi-user product connecting to *other people's* IBKR accounts — that makes it a third-party vendor in IBKR's terms, requiring separate IBKR compliance approval, out of scope for MVP. Because `BrokerAdapter` is already an interface, this is a future adapter class if/when needed, not a rearchitecture. See `SIGNAL_ALPHA_DESIGN.md` §9 for the full decision record.
- [x] **Real portfolio context.** *(Red-team #4)* — Split into two independent pieces with different risk profiles, handled differently:
  - **Earnings calendar: wired in live.** `data/finnhub.py::fetch_next_earnings_date(ticker)` calls Finnhub's `/calendar/earnings`, returns the earliest upcoming date in the next 90 days (or `None` if unset/unavailable/no API key — same safe-default pattern as `fetch_company_news`). `orders/service.py::build_risk_context()` now calls it instead of hardcoding `earnings_date=None`. `risk/rules.py::check_earnings_proximity` was already fully implemented and in `RULES` — it was dead code waiting for real data, not new logic, so this was low-risk to wire in now rather than deferring to Phase 4.
  - **Real IBKR account state: built, deliberately NOT wired in.** New `portfolio/ibkr_provider.py::IBKRPortfolioProvider.get_snapshot()` calls `IBKRClient.get_accounts()` → `get_ledger()` (new method added to `data/ibkr.py`) → `get_positions()` and returns a `PortfolioSnapshot` (net_liquidation, cash, position_values, `as_of`, `is_stale(max_age_seconds)`), or `None` if the gateway is unreachable/unauthenticated/incomplete — never a fabricated partial snapshot. This is **not** called from `orders/service.py::build_portfolio_state()`, which still reads paper trades + `settings.paper_account_equity` and is what risk sizing actually uses today. Reasoning: Phase 3 paper trading is meant to stay virtual (`CLAUDE.md`: "No live trading code until Phase 4"); wiring real account dollars into paper risk sizing now would blur that line without a corresponding Phase 4 decision to go live, and mirrors the adapter-isolation precedent above (build the seam, don't wire it until the phase that needs it). `IBKR_PORTFOLIO_MAX_STALENESS_SECONDS` config added (default 300s), inert today — nothing reads it since no live path calls the provider yet.
  - Verified with mocked `IBKRClient`/Finnhub responses (no local IBKR Gateway session available in this environment) plus real calls against the dev Postgres via `SessionLocal`: `get_snapshot()` returns `None` with no gateway running; a mocked client produces a correct `PortfolioSnapshot`; `is_stale()` thresholds correctly; `fetch_next_earnings_date` returns `None` with no API key configured and picks the earliest date from a mocked multi-row response; `build_risk_context()` with a mocked near-term earnings date produces a `RiskContext` that `check_earnings_proximity` correctly fails with `severity="needs_manual_review"` (not `"block"` — confirmed against the actual rule, which treats earnings proximity as review-required rather than an outright block), and a far-future earnings date correctly passes.
  - **Not implemented**, out of scope for this pass: staleness-blocking previews (i.e., actually calling `is_stale()` and rejecting a preview) — there's no live caller to block yet, since the provider isn't wired into any request path. Revisit when Phase 4 decides how/whether real account state feeds risk sizing.
- [x] **Tamper-evident audit log.** *(Red-team #6)* — Done: `audit_log` gained `prev_hash`/`entry_hash` columns (migration `f1a4b6c8d0e2`, nullable so pre-existing unchained rows aren't retroactively faked — none existed in dev, but a live deployment could have some). `audit/service.py::log()` now hashes each row (SHA256 over `prev_hash` + actor/action/entity_type/entity_id/details, canonicalized JSON) and links it to the previous row's hash, using `SELECT ... FOR UPDATE` on the chain tail to stop concurrent writers from forking it. `audit/service.py::verify_chain()` walks the whole table and recomputes every hash; a new `GET /api/v1/audit/verify` endpoint exposes it. Verified against the real dev DB: an empty chain verifies trivially; three chained writes link correctly (`e2.prev_hash == e1.entry_hash`, etc.) and verify clean; directly mutating one row's `details_json` in the DB (bypassing `log()` entirely) is caught by `verify_chain()`, correctly identifying the tampered row id. Also confirmed the endpoint works end-to-end through the running dev server.
  - Scope is honest, not complete: this detects tampering, it doesn't prevent it — anyone with direct DB write access could recompute the entire chain to hide an edit (documented in the module docstring). A real prevention story needs an append-only store or an external anchor (e.g. periodically publishing the chain tip hash somewhere outside Postgres), which is out of scope for a single-Postgres MVP. Also **not implemented**, per the original ask: request/trace id correlation and a source-data snapshot hash (hashing the upstream data — e.g. the scan/price bars — that a decision was based on, not just the decision itself). Both are additive later — they'd extend `log()`'s inputs, not change the chaining design.

## Phase 4 (live trading) — unchanged scope, now with explicit gate criteria

From `CLAUDE.md`: "Human-approved live trading via IBKR." Add to the existing gate:
- [x] Must not ship until the Phase 3→4 gate above is fully checked off. — All three items above are now `[x]`.
- [ ] Must not ship until paper trading has run for a meaningful stretch (weeks, not days) with the *upgraded* fill model and no risk-engine bugs found (per `SIGNAL_ALPHA_DESIGN.md` Milestone E). **Not satisfiable by code** — this requires real elapsed time running the paper system, not implementation work. To make that evidence easy to check as time passes, added `GET /api/v1/reports/paper-trading-health` (`reports/paper_trading_health.py`): aggregates `order_previews`/`risk_evaluations`/`paper_trades` (optionally filtered by `since=`) into status/verdict/fill-status distributions, closed-trade win rate, avg P&L%, avg entry slippage vs. the theoretical (naive limit-price) fill, and `days_of_history` (time since earliest recorded activity) — the last one being the direct measure against this gate's "weeks, not days" bar. Read-only, not part of any order/risk decision path. Verified against the real dev DB: aggregation counts/win-rate/avg-pnl/avg-slippage all correct against known synthetic rows (created and cleaned up in the same test); `since=` filtering excludes rows correctly; confirmed end-to-end through the running dev server with `X-API-Key` auth.
- [ ] Explicit "you are about to place a REAL order" confirmation UX; IBKR paper account for staging before real money. **Deliberately not started** — this is the first actual live-execution build item (would mean implementing `IBKRAdapter.submit_order` for real), and per `CLAUDE.md` ("No live trading code until Phase 4") plus the still-unmet gate above, we're holding off rather than overriding the gate the project itself defined. Revisit once the paper-trading track record above is actually established.

## Phase 5 (limited automation) — no change, notes only

- [ ] **Agent tool/gateway layer** (`scan_market`, `propose_trade`, `get_risk_evaluation`, `disable_agent`, etc., per `SIGNAL_ALPHA_DESIGN.md` §7) does not exist yet. Needed before any external agent (Claude, ChatGPT, etc.) is given scoped access to this system. Not required for Phase 3/4. Per this doc's own instruction to scope (not build) this before Phase 5 starts, and consistent with holding off on Phase 4 live-execution code until its gate is met: this pass only produces scoping notes below, no gateway code, no new agent-facing endpoints, no scope/permission enforcement mechanism. Building the actual dispatcher is Phase 5 work.
  - **Scoping notes — mapping §7's tool table to what already exists:**
    - `read_market_data`/`scan_market` → `routers/scanner.py`, `routers/universe.py` (READ_MARKET). Already exist as plain REST endpoints; a gateway would just be a thin wrapper, low risk.
    - `read_portfolio`/`read_positions` → `orders/service.py::build_portfolio_state`, `routers/paper_trades.py` (READ_PORTFOLIO). Same — already exist, paper-only today (no live equivalent is wired, see "Real portfolio context" above).
    - `read_news` → `data/finnhub.py::fetch_company_news` (READ_NEWS). Exists as an internal function, not currently exposed as its own REST endpoint — would need a thin route added, not new logic.
    - `generate_thesis` → `routers/thesis.py` (PROPOSE). Already gated by `settings.thesis_min_score` and dedup'd via `input_hash`; exists.
    - `propose_trade`/`preview_order` → `orders/service.py::create_preview` (PROPOSE, `requires_risk_check=True`). Exists; already always runs the risk engine and always persists (`OrderEvaluationRecord`/`OrderPreview`) whether approved or not — matches §7's "logging is not optional" requirement structurally, just not through a gateway dispatcher yet.
    - `place_paper_order` (§7: `PAPER_EXECUTE` scope, agent-invocable) → **this is the one real open decision, not just missing plumbing.** `orders/service.py::approve_preview` today requires a human `X-Actor` identity via `require_actor` on *every* approval, regardless of `AgentControl.autonomy_mode` — `CLAUDE.md`'s rule ("`paper_trades.status` is gated — `pending_approval` → `open` only after human approval") does not carve out an exception for `paper_only` mode. §7's design sketch implies an agent *could* call `place_paper_order` directly once granted `PAPER_EXECUTE`. Those two are in tension: either `CLAUDE.md`'s rule needs an explicit amendment scoping it to *live* trades only (paper stays human-gated always, contradicting §7), or `paper_only` autonomy mode needs to be defined as "agent can execute paper trades without a human clicking approve, but a human already turned on `paper_only` mode as the standing authorization." **Not resolved here — flagging as a decision for whoever scopes Phase 5 for real, not making it unilaterally.**
    - `request_live_approval` (PROPOSE, queues only) / `place_live_order` (LIVE_EXECUTE, never agent-invocable) / `cancel_order` (LIVE_EXECUTE) → all live-execution-adjacent, blocked by the same Phase 4 gate as the rest of live trading; `execution/ibkr_adapter.py::IBKRAdapter` remains the only seam, per its own docstring.
    - `get_audit_log` → `routers/audit.py` (READ_PORTFOLIO per §7, arguably should be its own scope). Exists.
    - `disable_agent` (ADMIN) → **built** (see below), independent of the gateway.
  - **A present-tense gap this scoping surfaced, not deferred to Phase 5:** `broker/auth.py::require_actor` is a single shared secret (`X-API-Key`) with an `X-Actor` free-text label — it does not distinguish a human caller from an automated one. Nothing in the current API stops a script holding today's API key from calling `POST /orders/{id}/approve` programmatically right now; the "human approval" guarantee in `CLAUDE.md` is enforced by convention (only a human has the key / only the frontend calls it) not by the auth layer. This isn't new risk introduced by Phase 5 planning, but §7's `ToolScope` model assumes a caller-identity distinction that doesn't exist yet in `require_actor` — real scope enforcement can't be bolted on without that first. Not fixing this now (no evidence it's been exploited, and doing so is real auth work, not a quick add) — recording it here so it isn't lost.

## Explicitly out of scope / do not build early

Carried over from both reviews, consistent with `SIGNAL_ALPHA_DESIGN.md` §14:
- Live IBKR execution, auto-approval, options, margin, shorting, or trading on LLM confidence alone before the gate above is met.
- Public deployment without auth (blocks even Phase 3 demo access beyond localhost/trusted users).
- "AI broker" / "Stock Broker" positioning in user-facing copy — product is a control plane, not a broker. Naming/positioning cleanup is low-priority polish, not a P0.
